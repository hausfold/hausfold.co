Every page above this one documents a **room**: a nix-darwin module under
`modules/`, plus three lines of registry that put it in the option reference,
the agent skill and the generated host file at once.

Most of the time you want no room, and
[Customizing](/docs/haus/desktops/customizing) is the cheaper path. A room
earns its existence when a package, its launchd job, its config file, its
theming and the options steering all four have to move and switch as one.

<Callout title="Your machine, or the layer?">
If it only ever runs on your Mac, write a plain module, name its options
**`haus.my.*`**, and set them from your **host file**, never a desktop, which
is a file other people run without your room. haus promises never to ship a
room under that prefix, and a flake check holds the promise. Under a plain name
you race a future release, silently: two modules declaring
different leaves under one namespace merge with no error, one room's switch
steering the other's. Your Mac warns you once. Publishing drops the prefix for
a plain `haus.<name>`, the name a stranger types after
[`haus add --room --namespace <ns>`](/docs/haus/reference/haus#pinning-a-room).
</Callout>

## The two files

```
modules/kettle/
  options.nix     # what a host may say
  default.nix     # what happens when they say it
```

`options.nix` declares `options.haus.kettle` and touches no `pkgs` and nothing
from darwin, so Linux CI can evaluate the option surface alone and render it
into the reference page, the `haus` agent skill and a fresh install's annotated
host file. `default.nix` wraps its whole body in `lib.mkIf cfg.enable`.

<Callout type="warn" title="Why the options can't live in default.nix">
An option declared inside that gate vanishes exactly when the module system
needs it to decide the condition. Hence the split, and hence
`modules/options-modules.nix`, one list of every room's `options.nix` that the
renderers and `modules/default.nix` all read.
</Callout>

## Three lines of registry

`modules/options-groups.nix` **fails closed**: the `room-registry` flake check
compares it against the evaluated option tree, so a namespace or leaf it
doesn't mention is an error. A room owes it:

1. **Every public leaf**, by exact path, under `optionPaths`. An inventory, not
   a glob, so a new option fails loudly. Identity, secrets, tokens and hardware
   ids are a host's: mark those leaves host-only and no shared desktop can set
   them.
2. **An owner**, in `roomOwners`. Two namespaces can share one room:
   `haus.bar` and `haus.menuBar` are both the Bar.
3. **A blurb** and an `order`, in `groups`: the sentence a catalogue is laid
   out from, and where the room sits in it.

Then the options file into `modules/options-modules.nix`, the implementation
into `modules/default.nix`, and regenerate the committed metadata that the
`site-data-current` check compares against and this site renders from:

```sh
out=$(nix build --no-link --print-out-paths .#site-data)
install -m644 "$out"/*.json docs/site-data/
```

## Rooms offer, never reach

**A room may offer something to another room, and may never reach into one.**
No room reads another's settings, and none switches another on. The receiver
declares a slot, an *extension point*, and draws what it finds there inside its
own enable gate:

```nix
# in the RECEIVING room's options.nix, here the Bar's
haus._contrib.bar.brewStatus = contrib.mkExtensionPoint {
  description = "A pill the Kettle room asks the bar to draw.";
  options = { … };
};
```

The path is an address: who receives, then what is offered. The asker is not in
it, so either room can switch off without touching the other. That middle
segment names the receiving **room**, not a namespace, so the Bar's slot is
`_contrib.bar.*` under either of its two. The underscore means wiring rather
than a setting, and the renderers prune it.

It is also what makes a standalone `darwinModules.<room>` import work: the bare
foundation plus that one room, and nothing dragging its neighbours in.

## Default to off, and mean it

An optional room's `enable` defaults to `false`, always. A
[desktop](/docs/haus/desktops/choosing) is a *complete* answer, not a diff, so
a `true` default grows silently into every desktop that never heard of your
room. `core` (macOS itself) and `terminal` (the shell) have no switch on
purpose: they are the floor, not furniture.

## Prove it

```sh
nix flake check
nix eval .#darwinConfigurations.example.system.drvPath
```

The first runs the registry check, the desktop seam, the keymap collision check
and the rest; the second evaluates a whole machine, which is what catches an
option that type-checks and then contradicts another room. Neither activates.
[`haus plan`](/docs/haus/reference/haus) shows what a real rebuild would change
without changing it.

<Callout type="warn" title="A new option owes a docs page">
The layer and this site are two repositories, and nothing fails when they
disagree. A new room owes a page under `content/docs/haus/rooms/`, an entry in
that tree's `meta.json`, and an icon; a changed keybinding owes an edit to
[Keys](/docs/haus/rooms/keys). The reference page regenerates itself; the prose
does not.
</Callout>

## What a room may not do

- **Hold a colour.** Hexes live in
  [nebelung](https://github.com/hausfold/nebelung); a room reads the palette.
- **Hold an app's own logic.** A room installs and configures the app; it is
  not the app.
