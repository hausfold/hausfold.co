**Windows** is the tiling room. Windows arrange themselves into a tree instead of
piling up, and the keyboard moves them around it: launch, focus, resize, throw
one to another workspace, without reaching for the mouse. It feels like a tiling
Linux rig; underneath it is still native macOS windows, driven by
[AeroSpace](https://github.com/nikitabobko/AeroSpace).

Two keys carry almost all of it:

- **⇪ Caps-Lock is the leader.** Tap it and the bar turns into letter hints;
  press an app's letter to launch or focus it. It is also the door to moving
  focus, resizing, and jumping workspaces.
- **⌥ Option is the everyday modifier**, for layouts and workspace moves.

Focus-by-arrow deliberately sits *behind* the leader rather than on a bare `⌥`
chord: `⌥`, `⌘` and `⌃` with the arrow keys are all macOS text navigation, and a
window manager that took them would break typing everywhere. It is also the
better motion of the two, because the first arrow latches into navigate mode and
the ones after it keep moving without re-tapping anything.

<Callout title="No Vim keys, by default">
`⌥H/J/K/L` used to focus by direction as well, and no longer does. haus binds no
`h`/`j`/`k`/`l` direction anywhere out of the box: the arrows already do it
better, and four chords that duplicated them were four chords not reaching your
terminal. If you want them, `haus.keys.leaderExtras` puts them behind the
leader:

```nix
haus.keys.leaderExtras = [
  { key = "h"; command = "aerospace focus left";  caption = "Focus left"; }
  { key = "l"; command = "aerospace focus right"; caption = "Focus right"; }
];
```

Pick letters no app in your roster has claimed; a rebuild refuses a collision
rather than letting one binding shadow the other.
</Callout>

## Enable it

```nix
haus.windows.enable = true;
haus.keys.leader = "caps";     # or "none" to keep Caps Lock as Caps Lock
haus.keys.windowNav = "alt";
```

## Tap ⇪, then

| Key | What happens |
|---|---|
| `<app-key>` | Launch or focus that app: `T` terminal, `B` browser, and whatever else you add |
| `1`–`4` | Go to that numbered workspace. Four out of the box; [more of them](#the-numbered-ones) if you want them |
| `⇧` + a workspace key | **Throw** the focused window there and follow it |
| `⌥⇧` + a workspace key | Throw it there and **stay** where you are |
| `←↓↑→` | Move focus, and stay in navigate mode so arrows keep working |
| `-` / `=` | Shrink / grow, repeatably |
| `V` / `F` | Clipboard history / Find Files, via the [launcher](/docs/haus/rooms/launcher) |
| `Z` | Reopen the last closed app |
| `,` | macOS System Settings: the `⌘,` convention, one level up |
| `.` | Cycle this workspace's tiling: columns → grid → accordion ([below](#spin-the-layout-until-its-right)) |
| `` ` `` | Re-sort every window to its workspace |
| `/` | The cheatsheet |
| `Esc` | Out |

A **workspace key** is a digit, or the letter a
[named workspace](#workspaces-and-what-lives-on-them) claimed. Out of the box
those letters are `T` and `B`, which is why the throw usually looks like it hangs
off the app you were going to open.

The `⇧` row is the one worth learning: going somewhere and taking the window
with you is the same motion one `⇧` apart. Adding `⌥` is the third verb, sending
something away without going with it, which is the move for clearing a workspace
you are still working on.

`⌥⇧` rather than the `⇧⌘` you might expect: `⇧⌘3`, `⇧⌘4` and `⇧⌘5` are macOS's
own screenshot shortcuts and win over anything a window manager binds, so that
chord would have worked on some digits and not others.

## Without the leader

| Keys | What happens |
|---|---|
| `⌥/` | Tiles layout; toggles the split horizontal ↔ vertical |
| `⌥,` | Accordion layout |
| `⌥F` | Fullscreen, and the bar says so ([unless the window is alone](#a-window-on-its-own-does-not-zoom)) |
| `⌥` + right-click | Fullscreen the window **under the pointer** ([below](#zoom-the-window-youre-pointing-at)) |
| `⌥⇧Tab` | Move this workspace to the next monitor |
| `⌥⇧;` | **Service mode**: `R` flattens the tree, `F` floats a window, `Backspace` closes every other window, `⌥⇧←↓↑→` joins a neighbour |

## Zoom the window you're pointing at

`⌥F` can only ever reach the window you are *in*. Its pointer twin reaches the
one you're pointing at:

```nix
haus.windows.mouseFullscreen = "right";   # right | left | none
```

**⌥ + right-click** now zooms whichever window is under the cursor to fill its
own workspace, including one on another monitor, which by keyboard would mean
going there first. It's the same AeroSpace fullscreen, so it's a toggle: the
same click puts the window back. ([Not a window on its
own](#a-window-on-its-own-does-not-zoom), same as `⌥F`.)

The modifier isn't separately settable: it follows `haus.keys.windowNav`, so
the click and `⌥F` stay one vocabulary and a machine that moved the modifier for
its keyboard layout moves the click with it.

<Callout type="warn" title="This spends a gesture machine-wide">
The click is consumed over **every** app, not just tiled ones, which is why the
default is the quietest of the three rather than a free one. `"right"` still
costs you macOS's ⌥ *variant* of a context menu (inside a Finder window ⌥ is
what turns "Copy X" into "Copy X as Pathname") and ⌥ + right-**drag** where an
app uses it, since the mouse-down is swallowed before the drag starts. Clicking
the desktop is unaffected.

`"left"` is offered for mice where the right button is awkward, and costs
considerably more: multi-cursor in GUI editors, ⌥-click-a-link to download,
⌥-click on a menu extra, and every ⌥-drag. There is deliberately no `ctrl`
value: ctrl+click **is** macOS's secondary click, and binding it would cost you
context menus everywhere.
</Callout>

Clicking the desktop passes straight through, so you keep Finder's menu there,
and anything drawn above ordinary windows (the menu bar, the Dock, the
[bar](/docs/haus/rooms/bar)) is transparent to the chord rather than being
"clicked".

The chord is carried by [pounce](/docs/pounce)'s event tap, because AeroSpace has
no mouse bindings at all, so it needs `haus.launcher.enable` and the
Accessibility grant the palette already asks for. Both are true on
[hacker](/docs/haus), which sets `"right"` out of the box.

`⌥Tab` is deliberately unbound:
[pounce](/docs/pounce/beyond-launching#a-window-switcher-not-an-app-switcher)'s `⌘Tab` answers the same question
better, with a most-recently-used list of *windows* that goes as far back as you
like and gathers its rows by workspace.

<Callout title="Windows untangle after sleep">
macOS scrambles window positions when the machine wakes. windows watches for that
and puts them back on its own: the right workspace *and* the tiled layout, so a
window that came back floating at some arbitrary size joins the tiles again.
<kbd>⇪</kbd> then <kbd>`</kbd> does it on demand, which is the repair to reach
for any time a window ends up somewhere or some size it shouldn't be. Apps you
told to float stay floating.
</Callout>

## A window on its own does not zoom

Fullscreen is a *mode*, not a size. Arm it on a workspace holding one window and
nothing looks different, because that window already fills the workspace. What
would change is invisible: the workspace would be flagged fullscreen from then
on, the next window you opened there would open *behind* this one, and the bar
would wear the fullscreen glyph the whole time for a mode that meant nothing.

So both paths decline it. `⌥F` and `⌥` + right-click zoom a window only when
AeroSpace says it has company on its workspace. Turning fullscreen back **off** is always allowed,
including for a window whose siblings have since closed, because that is the way
out of the mode.

If a press looks like it did nothing, count the windows on that workspace. One is
the answer.

## Not fond of these keys?

None of it is baked in. Three options move the whole vocabulary at once:

```nix
haus.keys.leader    = "caps";       # caps | alt-space | none
haus.keys.windowNav = "alt";        # alt | ctrl-alt | cmd-alt | none
haus.keys.palette   = "cmd-space";  # cmd-space | alt-space | ctrl-space | none
```

The three reasons people change them:

- **Keep Caps-Lock as Caps-Lock.** `leader = "alt-space"` gives you the launcher
  without remapping the key.
- **A non-US layout.** On many layouts `⌥`+letter is how you type an accented
  character, so a window manager owning `⌥` makes the keyboard unusable.
  `windowNav = "ctrl-alt"` moves every chord in one go, and the cheatsheet
  moves with it, because both are generated from the same table.
- **Mouse-first.** `leader = "none"` with `windowNav = "none"` leaves the
  keyboard entirely alone: windows still tiles, but claims no chords.

`palette = "none"` stops haus taking ⌘Space from Spotlight; it's the only value
that takes it. On a machine that already ran with it, re-enable Spotlight's
shortcut yourself in System Settings ▸ Keyboard ▸ Keyboard Shortcuts; nothing in
haus gives it back.

Whatever you pick, the in-system cheatsheet (tap the leader, then `/`)
describes the keys you actually have, not the defaults above.

## Workspaces, and what lives on them

A workspace is a named place with apps that belong to it. Declare one, and its
apps' windows move there by themselves:

```nix
haus.workspaces.comms = {
  key = "c";                       # ⇪ ⇧C throws the focused window here
  icon = ":slack:";                # the bar pill's glyph
  apps = [ "slack" "discord" ];    # roster ids
};
```

The attribute name **is** the workspace id: a letter like `T`, or a word like
`comms`. Three fields:

- **`apps`**: [roster](/docs/haus/rooms/apps) ids that live here.
  Launching any of them from the leader lands you here. An app belongs to at
  most one workspace, and naming an id that isn't in the roster warns rather
  than failing quietly.
- **`key`**: the throw key: `⇪ ⇧` to throw and follow, `⇪ ⌥⇧` to throw and stay.
  There is no bare-key binding for a
  workspace: that namespace belongs to the launcher letters, one of which
  usually doubles as "open something here". `null` means the workspace is
  reachable only by launching an app that belongs to it.
- **`icon`**: a [SketchyBar app-font](https://github.com/kvndrsslr/sketchybar-app-font)
  ligature like `:slack:` for the bar's pill; any other string is drawn in the
  bar's own font.

The launcher letters themselves come from `haus.roster`, the one list that also
says where each app is installed from; that's [the Apps room](/docs/haus/rooms/apps).
Out of the box the only letters taken are `T` for the terminal and `B` for the
browser.

### The numbered ones

Four numbered workspaces exist alongside whatever you name, whatever any app
claims. If four isn't your number:

```nix
haus.windows.numberedWorkspaces = 6;   # 0 to 10
```

Ten is the ceiling because the leader reaches a workspace by pressing a **digit**
and there are ten of those: `1` through `9` in order, then `0` for the tenth, the
same wrap a browser's tab shortcuts use. `0` is a legal count and means no
numbered workspaces at all, for a machine where every workspace is one you named.

Each one you add takes its digit in launch mode, so a `haus.workspaces` key that
collides with a newly claimed digit is refused at rebuild rather than silently
losing one of the two bindings. Raising the count never renames an existing
workspace, so nothing moves.

## Tiles or accordion

A fresh workspace splits the space between its windows. The other layout stacks
them and gives the focused one the room, leaving a sliver of its neighbours
showing, which reads more like a browser's tabs and survives better on a laptop
display where a third split stops being readable:

```nix
haus.windows.defaultLayout      = "accordion";  # or "tiles"
haus.windows.accordionPadding   = 80;           # points left for the neighbours
haus.windows.defaultOrientation = "auto";       # auto | horizontal | vertical
```

These are defaults, not locks: `⌥/` and `⌥,` still switch the workspace you
are on, and so does the ⇪ `.` dial ([below](#spin-the-layout-until-its-right)),
which carries accordion as one of its three stops. `defaultOrientation = "auto"` picks per monitor from its shape, side by side
on a wide screen and stacked on a tall one, which is right almost always; the
other two are for a machine that should split the same way whatever display it
wakes up on.

One more, off by default because it moves something you didn't:

```nix
haus.windows.mouseFollowsFocus = true;
```

The pointer follows keyboard focus, between windows as well as between screens.
Both halves are *lazy*: nothing moves while the pointer is already inside
whatever took focus, so it re-centres on the jumps that would have lost it and
sits still on the ones that wouldn't.

And one that IS on by default, because most of the time it saves you a keystroke:

```nix
haus.windows.gravity = false;
```

**Gravity** is what pulls you back to the most recently populated workspace when
the one you're on loses its last window. Both ways of emptying one count: a ⌘Q
that takes every window of an app at once, and closing the *last* window on a
page — a ⌘W on a lane, a ⌃D that ends a shell — while that app carries on in
windows elsewhere. The second matters most on the `T/<repo>` lane pages, which
are not persistent: without it you were left standing on a page that appears in
no list, with nothing on it.

It fires only for a workspace you *emptied*, never for one you deliberately
walked onto that happened to be empty. Turn it off if a screen changing without
you touching it is worse than a blank one:
[`haus.appearance.reduceMotion`](/docs/haus/rooms/appearance#motion) decides that
for you, since it is the largest unasked movement haus makes.

It needs the [bar](/docs/haus/rooms/bar) as well as this room: both tells live in
the bar's event stream and nowhere else, so with no bar there is no gravity
either way.

## Spin the layout until it's right

`⌥/` and `⌥,` change one split. **⇪ then `.`** reshapes the *whole* focused
workspace at once, advancing it one stop round three arrangements:

| Shape | What you get |
|---|---|
| **Grid** | √n columns, rounded up, with every column **widened in proportion to how many windows it holds** — so all of them end up the same size |
| **Accordion** | One flat row still, but the focused window takes the space and its neighbours are left as slivers either side — `accordionPadding` is how wide those slivers are |
| **Columns** | One flat row again, which is what a tiled workspace does on its own |

The order is columns → grid → accordion → columns, so from a plain workspace
one press deals a grid, two gets you the accordion, and three puts it back.

The grid is an exact shape rather than a bucketing, and the same shape every
time for a given number of windows:

| Windows | What you get | | Windows | What you get |
|---|---|---|---|---|
| 2 | Side by side | | 6 | 3 × 2 |
| 3 | One full-height third, then two stacked beside it | | 7 | A 2-stack, a 2-stack, a 3-stack |
| 4 | 2 × 2 | | 8 | A 2-stack and two 3-stacks |
| 5 | One full-height fifth, then a 2 × 2 | | 9 | 3 × 3 |

Above nine it keeps going by the same rule — √n columns, rounded up, dealt as
evenly as they divide — so there is no cliff, just more columns.

**Each workspace remembers its own shape.** The key reshapes whichever
workspace is focused, and that workspace is what remembers which shape is on, so
pressing `.` somewhere you have never used it deals a grid rather than
continuing a sequence you started elsewhere. Press it again on a shape you
already have and it reapplies fresh, which is the move once a new window has
wandered in.

The bar says which shape is on — a **Grid** / **Accordion** / **Columns** pill
beside the workspace and page pills, drawn only when the workspace holds more
than one tiled window. Clicking it advances the dial, same as the key. Because
the memory is per workspace, that pill is only ever describing the workspace you
are looking at.

Every press is **one shot**: it reshapes, then leaves you alone. Nothing runs in
between, so a resize you make afterwards stands until you press again.

Two things worth knowing. The accordion stop is **AeroSpace's own layout**
rather than a shape haus deals, which is why it is the one the bar reads live:
it is a fact about the workspace, so it holds for every window you open
afterwards instead of drifting the way a grid does. On a machine running
`defaultLayout = "accordion"` a fresh workspace therefore starts where the dial
would put it — one press from there deals a grid, and the second brings the
accordion back. And **floating windows are left alone** — they are not in the
tree the dial reshapes, so a terminal popup sitting over the tiling neither
moves nor counts toward the shape.

It is also a single reflow: the whole rearrangement is sent to AeroSpace as one
batch, so the windows travel straight from where they were to where they belong
rather than through every step on the way. Nothing takes focus, so the window
you were looking at is still the one you are looking at.

## macOS has its own opinion about windows

Stage Manager and edge-drag tiling answer the same question this room does, and
macOS turns edge-drag tiling **on** out of the box. So on a fresh haus machine
you have two window managers: AeroSpace tiles a window into the layout, and a
drag that merely passes near the screen edge hands half the screen to it. The
symptom is "windows won't stay where I put them", and it points at neither of
them on its own, which is why this room owns the settings rather than leaving
them with the rest of the macOS defaults:

```nix
haus.windows.nativeTiling.edgeDrag         = false;  # the one to turn off if you tile
haus.windows.nativeTiling.topEdgeFullscreen = false;
haus.windows.stageManager.enable            = false;
```

If you'd rather keep native tiling available and just stop it firing by
accident, add the ⌥ accelerator to the line above: it's a second, deliberate
way in, not a replacement for turning the bare drag off (the two keys are
independent, and macOS ships both on):

```nix
haus.windows.nativeTiling.edgeDrag          = false;  # no tiling on a bare drag
haus.windows.nativeTiling.optionAccelerator = true;   # ⌥-drag still tiles
```

haus **warns** when the tiler and either of these are on together, naming both
switches. It's a warning and not an error, because "Stage Manager on the laptop
panel, tiling on the external" is a real way to work.

The same group covers the desktop itself, which pairs well with a wallpaper you
chose to look at rather than to file things on:

```nix
haus.windows.desktop.hideIcons     = true;   # files stay in ~/Desktop
haus.windows.desktop.hideWidgets   = true;
haus.windows.desktop.clickToReveal = false;  # macOS 14's click-the-wallpaper behaviour
```

<Callout title="These land at your next login">
  This whole group writes `com.apple.WindowManager`, which macOS reads when your
  login session starts and never re-reads: there is no process to restart the
  way Finder or the menu bar can be restarted. **The write happens during the
  rebuild; the effect appears at your next login.** Nothing is half-applied in
  between, and `haus plan` tells you before the rebuild rather than after.
</Callout>

Every option here is unset by default, like every macOS setting haus curates.
Unset doesn't mean "off": it means haus writes nothing, so a choice you made by
hand years ago survives untouched.

## Turning it off

```nix
haus.windows.enable = false;
```

The Caps-Lock remap, the launcher and AeroSpace all stay out of the way. Nothing
else in haus depends on it; [Leaving](/docs/haus/leaving#switch-off-a-room)
does the same for the other rooms.

## Works with

- **[Bar](/docs/haus/rooms/bar)**: the workspace pills, and the letter hints
  the leader draws, are this room's contribution to the bar. No bar, no hints;
  the tiling itself is unaffected.
- **[Apps](/docs/haus/rooms/apps)**: a roster entry's `key` is what the leader
  launches, and its workspace is where its windows land.
- **[Launcher](/docs/haus/rooms/launcher)**: its opt-in `⌘Tab` window switcher
  answers the same question from the other side.
- **[Appearance](/docs/haus/rooms/appearance)**: `haus.appearance.reduceMotion`
  switches off both of this room's unasked movements: the pointer following
  focus, and gravity.
