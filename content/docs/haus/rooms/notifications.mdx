Every banner this desktop draws goes through `haus-notify`: to
**[trill](/docs/trill)** when trill answers on its socket, to Apple's banner when
nothing does. That runs on every haus machine, so no room waits on trill being
installed. This one asks only: **does haus own the bundle?**

## Enable it

```nix
haus.notifications.compositor = true;
```

```sh
haus rebuild
```

Off by default. There is no `haus.notifications.enable`: `false` would claim this
Mac draws no haus notifications, which is never true. With the room on, trill's
[agent skill](/docs/haus/rooms/ai) installs beside haus's; `false` again stops
the installing and updating, and deletes nothing.

## Why the path is fixed

The bundle is copied to **`/Applications/Trill.app`**, never run from the Nix
store: macOS keys a **Full Disk Access** grant to an app's path, and a store path
moves on every version bump, so a store-run trill would lose the grant on the
rebuild that installed the fix you wanted.

## What a rebuild does

**A trill you quit on purpose stays quit.** A rebuild with a new version swaps
the bundle and restarts the compositor without stealing focus, but only if it was
running when the rebuild looked, or has never run on this Mac. It says `trill:
left quit …` otherwise. That line, or a warning that the socket never answered,
means no compositor until `open -g /Applications/Trill.app` or your next login.
Apple's banners keep working meanwhile, trill's filtering does not, and a
question on its ledge has nothing to click.

## What it does not do

- **It does not put `trill` on your PATH.** haus answers `trill` on every
  machine: a wrapper execs the binary inside `$TRILL_APP`, else
  `/Applications/Trill.app`, else `~/Applications/Trill.app`. Point `$TRILL_APP`
  at a branch build to outrank both.
- **It does not decide what happens to any one notification.** That is
  `~/.config/trill/rules.json`, reloaded on save; haus adds no second dial. Every
  `haus-notify` send carries a `--source` (`haus.bar`, `haus.lane`, one per
  room), so "stop telling me about the bar reloading" is a line there, not a
  rebuild.
- **It does not own `~/.config/trill/config.json`.** It merges one key,
  `fontFamily`, from [`haus.fonts.sans.name`](/docs/haus/rooms/appearance#type),
  and leaves the file writable, so a family you pick in trill's settings sticks
  only until the next `haus rebuild` puts the desktop's back. A symlink or
  invalid JSON there is left alone, mentioned only on the rebuild's stderr.

## New mail

`haus.mail` holds an IMAP connection open with IDLE, so nothing polls: a card
lands a second or two behind the mail, drawn by `haus-notify` like every other
card.

```nix
haus.mail = {
  enable = true;
  address = "you@gmail.com";
  mailboxes = [ "INBOX" ];
};
```

`INBOX` is the one name IMAP standardises; the rest are your provider's spelling,
and Gmail's are bracketed (`[Gmail]/Starred`). haus refuses an empty list: it
would watch every mailbox on the account, so on Gmail one message arrives once
per label.

Then the password, once:

```sh
haus rebuild
haus-secret --check
```

`--check` asks for `MAIL_IMAP_PASSWORD` and keeps it wherever
[`haus.secrets.provider`](/docs/haus/rooms/security#secrets-your-rooms-need)
points, your login keychain by default. Google wants an [app
password](https://myaccount.google.com/apppasswords) here, not your account
password, and minting one needs 2-Step Verification. There is no OAuth: Google
expires an unverified app's refresh token weekly.

<Callout type="warn" title="An app password reads the whole mailbox">
It is static, so it belongs in the keychain, never your host file.
Revoking it on Google's page cuts this Mac off, and no other machine of yours
notices.
</Callout>

Until there is a password the watcher parks and says so in
`~/Library/Logs/haus-mail.log`.

### What counts as new

A mailbox nobody has watched records where it is, so turning this on draws no
card for what is already unread. After that a message must be unseen and newer
than the last this Mac announced, so your laptop stays quiet about mail you read
on your phone at breakfast.

More than five at once collapses into one card saying how many. On Gmail a card
carries an Open pill to the message's thread; elsewhere none. The mailbox is
opened read-only, headers only: nothing marks your mail as read, and no card
carries a preview.

### Check it without waiting for mail

`--test` draws a card for the newest message whatever the watermark says;
`--dry-run` prints one instead. Neither moves the watermark:

```sh
haus-mail-announce --mailbox INBOX --host imap.gmail.com \
  --address you@gmail.com \
  --password-command "haus-secret MAIL_IMAP_PASSWORD" \
  --state-dir ~/.local/state/haus/mail --test
```
