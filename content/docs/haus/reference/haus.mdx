`haus` is the command that drives your machine after install: it wraps the Nix
build and the activation you would otherwise run by hand, and joins your `PATH`
with the first successful switch. Run it with no argument and you get `haus
status`.

For the day-to-day shape of it, see
[Keeping it current](/docs/haus/keeping-it-current).

## Commands

| Command | What it does |
|---|---|
| `haus rebuild` | Build, then switch. Your everyday apply; a failed build never touches the running system. |
| `haus update` | Move the haus pin in `~/.config/nix/flake.lock` forward, upgrade the family's Homebrew apps, then rebuild. |
| `haus rollback [N]` | Return to the previous generation, or to generation `N`. |
| `haus generations` | List the generations you can roll back to. |
| `haus status` | The current generation, and how stale the pinned haus is. |
| `haus edit` | Open your host file in `$EDITOR`. |
| `haus set <path> <value>…` | Write a machine override, type-check it, rebuild once. |
| `haus set` | With no arguments: search every option this machine has, then pick or type the value. |
| `haus get [path]` | Print one declared value; with no path, list your overrides. |
| `haus unset <path>…` | Set nullable options to `null`, then rebuild once. |
| `haus reset <path>…` | Drop overrides and inherit the value underneath again. |
| `haus plan` | What the next rebuild would change, read-only. |
| `haus diff` | What the configuration you're *running* set, versus what macOS actually has right now. |
| `haus capture [cat…]` | Turn this Mac's current settings into config lines *and* a snapshot. |
| `haus revert-settings [snapshot\|list]` | Put a captured snapshot back. |
| `haus options` | Refresh `hosts/<host>/options.nix` (every `haus.*` option at its default, described and commented out) from the build this machine is running. |
| `haus doctor` | Health check: Nix, the Xcode CLT, the login agents, cask drift, every permission and click still waiting on you, your secrets, agent readiness. |
| `haus permissions` | Walk everything on this Mac that needs a person — one card at a time, what it is for, and a button. `--list` reports without touching anything. See below. |
| `haus btm` | On macOS Tahoe and later, check whether Background Task Management is blocking the login agents. |
| `haus tour [reset]` | Start the guided tour in the bar, or re-arm its first-run hint. |
| `haus show <src>` | Read a desktop or room (a local file, or a source you have not got yet) before you publish it, or before you trust one, and see what it would change on this Mac. Read-only; see below. |
| `haus add <src>` | Pin a desktop you found and select it, or a room with `--room --namespace <ns>`: writes `flake.nix` and `flake.lock`, never rebuilds. See below. |
| `haus desktop [name]` | List every desktop this machine can select (built in and pinned), or switch to one. |
| `haus remove <name> [replacement]` | Unpin a desktop or a room `add` brought in. A desktop falls back to `blank` if it was the one selected. |

## The things a rebuild cannot do for you

A few steps on a fresh Mac need a human, and macOS makes sure of it: a
permission is granted by a person clicking, or it is not granted. `haus
permissions` is the walk through them.

```sh
haus permissions          # one card at a time, with a button
haus permissions --list   # just the report; opens nothing, asks nothing
```

Each card says what the thing is for and what breaks without it, then offers
the shortest route to granting it — **the real macOS prompt** where the service
has one (Accessibility does, so Pounce's grant is one click and no trip to
Settings), and otherwise the exact System Settings pane, deep-linked. Then it
waits: go and click, come back, and the card has already gone green.

**It only ever tells you what it can actually see.** Some grants macOS lets a
program confirm — it asks, and a tick means macOS agreed. Others it exposes no
way to ask about at all, Automation above all, and those cards say so and are
marked done on your word rather than drawing a tick nothing earned. `haus
permissions --reset` forgets the ones you took that way; the measured ones are
unaffected, because they are re-measured every time.

**The deck is your machine's, not a fixed list.** Every room contributes the
steps it knows about, so you are shown the tiler's grant only if you run the
tiler, and a desktop that asks for nothing shows a deck with nothing in it. A
rebuild ends with a one-line count when anything is still waiting, and `haus
doctor` reports the same deck read-only.

## Changing a setting without opening an editor

```sh
haus set theme.accent teal
haus get theme.accent       # teal
haus reset theme.accent     # inherit the desktop's value again
```

**Only `haus.*` paths are writable this way.** The prefix itself is optional:
`theme.accent` and `haus.theme.accent` are the same path.
But a raw `system.defaults.*` or `homebrew.*` path, or an option that
doesn't exist, fails before any file is written. Those belong in your host file,
via `haus edit`. Values take the obvious shell form for strings and JSON for
booleans, numbers, lists and attribute sets.

`set` accepts as many pairs as you like and applies them in **one** rebuild:

```sh
haus set theme.flavor latte theme.systemAppearance flavor
```

That matters when one intent spans two options (light mode is haus's palette
*and* macOS's own appearance), because two calls would be two rebuilds with the
machine sitting half-switched in between. Multiple pairs are all-or-nothing:
one rejected value rolls the whole call back. `unset` and `reset` take lists for
the same reason.

The two undo verbs differ in one place. `reset` deletes the override, so
whatever your host file or desktop says underneath becomes effective again; a
path that had no override is reported and skipped rather than fatal. `unset`
writes `null` unconditionally, so it succeeds only where the option's type
admits `null`.

### When you don't know what it's called

Run `haus set` with no arguments and it asks instead:

```sh
haus set
```

The first prompt is a search over every option this machine's pinned haus has:
the path and a line of what it does, both searchable, so `light mode` finds
`theme.flavor` as readily as `flavor` does. The second prompt is shaped by the
option's own type: a closed set of values (an enum, a boolean) becomes a list
with today's value under the cursor, and anything else is a text box holding the
current default. Then it confirms, and hands the pair to the same `haus set`
you would have typed: same type-check, same rollback, same single rebuild.

Tab completion knows the same list: `haus set <TAB>`, and likewise for `get`,
`unset` and `reset`. Both read a static catalogue installed with your build, so
neither one evaluates your configuration to answer; they describe the revision
you have pinned, and `haus update` moves them with it.

### One key inside an option

A path may go *inside* an option rather than merely up to it:

```sh
haus set bar.items.aiUsage true              # one pill, not the whole bar
haus set displays.internal.uiScale larger-text
```

**Prefer the leaf.** Overrides are written with `lib.mkForce`, so naming the
enclosing set (`haus set bar.items '{"aiUsage":true}'`) forces the *whole*
set, and every pill you didn't name falls back to its own default.

A misspelled sub-option is refused before anything is written. Keys you invent
yourself (a display's UUID, say) are taken as given, and what sits under them is
checked instead. A path and one of its ancestors can't both hold an override:
the second is refused, naming the first and the `haus reset` that clears it.

### Where the setting lives

`haus set` writes an ordinary Nix module to
`~/.config/nix/hosts/<hostname>/settings/<path>.nix` and stages it: a git-backed
flake ignores untracked files, so staging is what makes it take effect. The file
*is* the setting: no database beside it, safe to read, edit or commit. Neither
`set` nor `reset` commits or pushes for you.

<Callout title="Also in the launcher">
The [launcher](/docs/haus/rooms/launcher)'s **Haus Settings** command is the same
mechanism behind three intent-sized buttons: *Make text bigger*, *Switch to
light mode*, *High contrast on*. The palette keeps no settings of its own; it
calls `haus set`.
</Callout>

## Reading a desktop or room before you trust it

`haus show` is the odd one out here: every other command drives *this* Mac, and
this one reads someone's work. It is what you run when a stranger hands you a
desktop, and what you run on your own before you publish one.

```sh
haus show ./writer.nix                     # a file you already have
haus show github:ada/writer-desktop        # one you don't
haus show git+https://git.example.org/ada/desktop
haus show file+https://example.org/writer.nix
```

A source is fetched into the Nix store and read there. Nothing in **your
config** is written: not your `flake.nix`, not your lock, not a vendored copy.
So `show` is safe to run on something you have every intention of refusing. If
the repo holds more than one desktop, `show` lists them and stops; name the one
you mean with `--file`.

It answers four questions and stops. **What class is it:** a desktop is data
haus can check, a room is a nix-darwin module and haus can tell you nothing
about what it does. **Does it pass**, with every rule it broke named, the same
rules [`checkDesktop`](/docs/haus/desktops/creating#prove-the-boundary) enforces
at rebuild time. **What does it set**, grouped by room, with the rooms it
says nothing about listed after, because what a desktop leaves alone is half
of what you are agreeing to. And, on a machine that has a haus config, **what
would change here**.

For a **fetched source** it tells you one more thing: where it came from. The
source as you typed it, the revision it resolved to, and two dates that are easy
to confuse: `changed`, the source's own commit date, and `fetched`, stamped from
the clock as this command ran. Nothing in a lock file records the second
one, which is why `show` has to.

### What would change here

A passing desktop is compared against your own machine, leaf by leaf, and the
first thing it prints is the part you cannot get from either file:

```text
becomes   ~/.config/nix · host mbp · desktop hacker.nix

  ⚠ 1 leaf your own config outranks — the desktop does not move it
    haus.theme.accent          stays "pink"   (it asks for "teal")

  changes   3 leaves
    haus.bar.enable            true → false
    haus.developer.languages   [ "node" ] → [ "rust" "go" ]   ⚠ a list:
                                              replaced whole, not merged

  turns off 19 leaves the desktop you have sets and this one does not
```

**A line in your host file outranks any desktop.** That is the ladder working as
designed (a desktop must lose to the person who chose it), but it means a
stranger's file can be full of opinions that do nothing on your Mac, and no
error anywhere says so. `show` names them first.

**A list your host names is replaced whole, not merged.** Lists only combine
between definitions of equal rank, so the desktop's entries do not add to
yours: yours simply win, all of them. It is the one interaction neither file
shows you.

Three things it will not guess at. A leaf inside a list-like option
(`haus.roster.<app>.key` and its kind) has no option of its own to rank, so the
values are shown and the winner is not; `haus plan` settles that. A leaf your
haus has never heard of is a **version gap**, not a bad desktop: it passed the
checker, which read the option registry your pin ships, so `haus update` is the
answer and not the file. And a leaf the desktop you have now sets and this one
does not goes back to *whatever haus decides*: the value underneath is not
recorded anywhere on your machine, so no number is printed for it.

This is a **leaf diff, not a rebuild preview**. Turning a room off moves
packages, files and services that nothing here counts;
[`haus plan`](#looking-before-you-leap) builds that answer. The comparison
evaluates *your* flake and never the stranger's (what crosses over is the list
of option names, not their file and not their values), and it still writes
nothing, including your lock: if your `flake.lock` would have to change to
answer, `show` says so and skips the section rather than resolving pins nobody
chose. `--no-diff` skips it outright, and a machine with no haus config never
sees it, which is what a publisher's CI wants.

A raw `file+https://` URL has neither: it pins content and nothing else, so
there is no revision to compare and no commit date to age. Worse than a missing
changelog, a later `nix flake update` on one prints the **same URL on both sides
of its arrow** while the content moves underneath. It reads as confirmation that
nothing changed. `show` says so where the shape is chosen, because
that is the cheap moment to publish from a repo instead.

<Callout type="info" title="Fetching and reading are two separate acts">
Reading a `.nix` file means **evaluating** it, and Nix evaluation is not inert:
a file can read other files and reach the network while it is being read. So
`show` splits the job. The fetch reaches the network and runs nothing: it pulls
a *tree*, never locking a flake, so not even a room's own `flake.nix` is
evaluated. The read reaches nothing: it runs restricted, where no fetch of any
scheme resolves and the only readable paths are the checker's own and the source
you named. An attempt to reach anything else fails loudly and names what it
reached for.

One honest limit: the restriction's unit is the store path, so a desktop fetched
from a repo can read the other files **its publisher shipped beside it**. It
still cannot read anything of yours. That is why the report attributes values to
the fetched tree rather than to one file in it.
</Callout>

<Callout type="warn" title="It proves *data*. It only ever reports *code*.">
A module function is reported as a room without being asked, because that
guess can only be over-cautious. Nothing is ever called a *desktop* because it
looks like one; that answer comes from the checker passing, never from the
file's shape. So a room is a warning, not a verdict: read it, or trust whoever
wrote it.
</Callout>

For CI, the exit code is the contract:

| Exit | Means |
|---|---|
| `0` | It is a desktop and it passed, or it is a room and you passed `--room`. |
| `1` | It was checked as a desktop and it failed; every rule is listed. |
| `2` | It could not be fetched or read, or the arguments were wrong. |
| `3` | It is code and you did not say `--room`, so nothing was checked. |

`--json` prints the whole report on stdout instead, with `class`, `checked`,
`ok`, `failures`, `sets`, `silent`, `origin` (`null` for a local file), and
`machine`, which is `null` whenever there was nothing to compare against and
otherwise carries one verdict per leaf (`changes`, `unchanged`, `overridden`,
`unranked`, `unknown`) plus the leaves your current desktop sets and this one
does not. On a machine that has no haus (a publisher's CI runner, say), the
same command is one `nix run` away:

```sh
nix run github:hausfold/haus#show -- ./writer.nix
nix run github:hausfold/haus#show -- github:ada/writer-desktop
```

## Pinning a desktop you found

`haus show` told you what it is; `haus add` is the command that actually
brings it in. It reruns the same check, and refuses whatever `show` would
have:

```sh
haus add github:ada/writer-desktop
```

That fetches it, checks it, prints the same report `show` would have, asks
`Add 'writer-desktop' from github:ada/writer-desktop and select it? [y/N]`,
then writes `flake.nix` (the input, and the `desktop` line) and
`flake.lock` in one edit. Nothing rebuilds; `haus rebuild` is the next
step, printed at the end.

```sh
haus add --as writer --file writer.nix github:ada/desktops   # name it, pick the file
haus add --vendor file+https://example.org/writer.nix        # copy it in, don't pin it
haus add --print git+https://git.example.org/ada/desktop     # show the edit, write nothing
haus add -y github:ada/writer-desktop                         # skip the prompt
```

`--vendor` is the old by-hand path (`curl`, `mv`, `git add`) done for you: the
file lands at `desktops/<name>.nix` in your config instead of becoming a flake
input, which is the right call for a one-off you plan to edit yourself.
Pinning is the default because it is how you get `haus update <name>` later.

Once it's in, three commands manage it the same way `haus rebuild` and
`haus rollback` manage your own machine:

```sh
haus desktop            # list what's pinned, and what's selected
haus desktop writer     # switch to a pinned (or built-in) desktop
haus update writer      # pull the latest writer, then rebuild
haus remove writer      # unpin it — falls back to blank if it was selected
```

Only one third-party desktop can be pinned at a time; a second `haus add`
prints the lines to add by hand rather than guessing at your `flake.nix`.

## Pinning a room

A desktop is data. A **room** is code: an ordinary nix-darwin module that can
install packages, write files and run activation scripts as root. `haus add`
takes one of those too, but only when you say so, and it never guesses which
`haus.<ns>` the room means to own:

```sh
haus add --room --namespace photography github:ada/photo-room
```

`--namespace` is required, and repeatable for a room that claims more than
one. It can't be inferred, because learning it means running the room's code,
which is the one thing this command won't do before you've agreed to it. Add
`--module <attr>` when the room's flake exports it as something other than
`darwinModules.default`. `--file` and `--vendor` don't apply: a room is a
flake input, not a file you can copy in.

<Callout type="warn" title="A room's confirmation is typed, and -y can't skip it">
Pinning locks the input, and locking a flake evaluates its `flake.nix`, so the
room's code has already run by the time anything lands in yours. That's before
any rebuild, which is why the prompt names the revision and asks you to type
its first twelve characters back. Neither `-y` nor `--yes` answers it. With no
terminal attached the answer is a per-name environment variable set to the
**full** revision, so a piped installer can never accept a room on your behalf
with one blanket switch. The name is `HAUS_ADD_ROOM_` plus the input's own
name, uppercased, with anything that isn't a letter, digit or underscore
turned into `_`: the `photo-room` above wants `HAUS_ADD_ROOM_PHOTO_ROOM`.
</Callout>

One room at a time, the same scope the desktop side keeps. `haus add --print`
shows the whole edit first (the input, the `extraModules` line, one
`haus._rooms.claimed.<ns>` per namespace) and writes nothing. `haus remove
<name>` takes the `extraModules` entry out along with the input, and then
deliberately stops short: it can't tell which namespace claim belonged to that
room, so it prints the `haus reset _rooms.claimed.<ns>` for you to run rather
than resetting a claim it might not own.

Either way nothing is applied yet. Locking ran the room's `flake.nix` and that
is all; `haus rebuild` is still the next step, printed at the end.

## Looking before you leap

`haus rollback` rewinds everything Nix owns, atomically. It does **not** rewind
macOS's own preferences: those are written imperatively during activation, into
`com.apple.dock`, Finder, `NSGlobalDomain` and friends, and no generation holds
them. Four commands close that gap:

```sh
haus plan        # what the next rebuild would change, before it changes it
haus diff        # what the running config set vs what macOS has right now
haus capture     # snapshot the settings a rebuild is about to move
haus revert-settings   # put that snapshot back
```

`capture` before a risky change and `revert-settings` after is the
macOS-defaults equivalent of a generation rollback. It defaults to the Dock,
keyboard and Finder; name a plist domain to reach anything else.

Both read the built activation script itself, and both probe macOS live for the
accessibility keys it accepts silently and then ignores, so neither is trusting
a plist or a hand-kept list.

`plan` reports five things, and the middle one is the one people expect to be
missing: packages, macOS settings, **the files written into your home** (with
the `onChange` hooks each would fire), launchd jobs, and new casks. Most of what
a desktop changes is neither a package nor a settings key: switching a bar pill on
moves a config file and nothing else, which no closure diff would show. The
handful of files written by an activation script rather than linked stay outside
that set and won't appear.

<Callout type="warn" title="`plan` reads your config directory, not the one you're standing in">
`haus` always evaluates `~/.config/nix` unless you tell it otherwise. Run `haus
plan` from a linked git worktree of that config (an agent lane, say) and it
previews the config on `main`, not the branch you're looking at. It warns and
names both paths; point it at the tree you mean:

```sh
HAUS_CONSUMER="$(git rev-parse --show-toplevel)" haus plan
```
</Callout>

## The one rebuild it refuses

If your host file writes `system.defaults.universalaccess.*` directly, `haus
rebuild` refuses to run whenever the app it runs under lacks Full Disk Access:
that write would abort activation partway and take every background service down
with it. The grant belongs to the app, not to you, so this catches a plain
terminal nobody has granted just as surely as an agent pane, and lets an agent
pane inside a granted terminal through.

Sidestep it with `haus.accessibility.*`, which reaches every key in that domain
macOS actually honours (all seven, which since August 2026 is every key
nix-darwin types there) with a guarded write. Otherwise run the
command from an app that holds the grant, or set `HAUS_FDA_ANYWAY=1` when you
know better. `haus plan` says which grant a rebuild wants before it runs.
[Changing your Mac with an agent](/docs/haus/agent-rebuilds) has the
detail.

## The other CLIs

`haus` is the only command an end user needs. One more arrives with the room
that wants it: `haus.ai.enable` brings **`holt`**
([the AI room](/docs/haus/rooms/ai)), agent worktrees for any repo.
