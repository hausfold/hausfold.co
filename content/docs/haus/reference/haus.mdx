`haus` drives your machine after install, wrapping the Nix build and the
activation you would otherwise run by hand, and joining your `PATH` with the
first successful switch. With no argument you get `haus status`. It is the only
command an end user needs; `haus.ai.enable` adds one more, **`scruff`** ([the AI
room](/docs/haus/rooms/ai)), and is also what puts `haus fix` on this list.

## Commands

| Command | What it does |
|---|---|
| `haus rebuild` | Build, then switch. A failed build never touches the running system. |
| `haus fix` | Hand the rebuild that just failed to a coding agent ([below](#when-a-rebuild-fails)). |
| `haus update [name]` | Move the haus pin in `~/.config/nix/flake.lock` forward, upgrade the family's Homebrew apps, then rebuild. With a name, that pinned desktop instead. |
| `haus rollback [N]` | Back to the previous generation, or to generation `N`. |
| `haus generations` | What you can roll back to. |
| `haus status` | The current generation, and how stale the pinned haus is. |
| `haus edit` | Your host file in `$EDITOR`. |
| `haus set <path> <value>…` | Write an override, type-check it, rebuild once. With no arguments, search every option this machine has and pick ([below](#changing-a-setting-without-opening-an-editor)). |
| `haus get [path]` | One declared value; with no path, your overrides. `--json` for the same as data. |
| `haus unset <path>…` | Set nullable options to `null`, then rebuild once. |
| `haus reset <path>…` | Drop overrides and inherit the value underneath again. |
| `haus plan` | What the next rebuild would change ([below](#looking-before-you-leap)). |
| `haus diff` | What the configuration you're *running* set, versus what macOS actually has right now. |
| `haus capture [cat…]` | This Mac's current settings as config lines *and* a snapshot. |
| `haus revert-settings [snapshot\|list]` | Put a captured snapshot back. |
| `haus options` | Refresh `hosts/<host>/options.nix` from the build this machine is running: every `haus.*` option at its default, described and commented out. |
| `haus doctor` | Nix, the Xcode CLT, background jobs wanting attention, cask drift, every permission still waiting on you, the theme ports, your secrets, agent readiness. |
| `haus report` | haus's issue form, with this Mac's details and its whole `haus doctor` report already in the diagnostics field. `--print` opens no browser. |
| `haus skill [name]` | haus's own agent skill, the file that teaches a coding agent to change this Mac; with a name, one of its reference pages. Always the copy rendered from the revision you pinned. |
| `haus skill install` | Write that skill into every agent client here that hasn't got it. `--client claude\|codex\|opencode\|pi` for one, `--dir <path>` for elsewhere. [`haus.ai.skill`](/docs/haus/rooms/ai) has normally done it already. |
| `haus permissions` | Everything that needs a person, one card at a time ([below](#what-needs-a-person-and-what-runs-itself)). `--list` reports without touching anything. |
| `haus services` | Every background job this Mac runs, and where each one logs. |
| `haus btm` | On macOS Tahoe and later, whether Background Task Management is blocking the login agents. |
| `haus tour [reset]` | Start the guided tour in the bar, or re-arm its first-run hint. |
| `haus show <src>` | Read a desktop or room before you trust it ([below](#reading-a-desktop-or-room-before-you-trust-it)). Read-only. |
| `haus add <src>` | Pin a desktop and select it, or a room with `--room --namespace <ns>`. Writes `flake.nix` and `flake.lock`, never rebuilds. |
| `haus desktop [name]` | Every desktop this machine can select, built in and pinned, or switch to one. |
| `haus remove <name> [replacement]` | Unpin a desktop or a room. A desktop falls back to `blank` if it was the one selected. |

## What needs a person, and what runs itself

A permission is granted by a person clicking, or it is not granted.

```sh
haus permissions          # one card at a time, with a button
haus permissions --list   # just the report; opens nothing, asks nothing
```

Accessibility has a real macOS prompt, so Pounce's grant is one click; the rest
deep-link a System Settings pane. **It only ever tells you what it can actually
see.** Automation above all exposes no way to ask, so those cards are marked
done on your word, and `haus permissions --reset` forgets only those.

`haus services` is the other half, its log paths read off the plists that
shipped rather than guessed at. A job that should be running but isn't comes
with the `launchctl kickstart` line that starts it again, but **idle is often
the right answer**, and each line says which kind of idle it is.

Every room contributes its own steps and jobs, so both decks are your machine's
rather than a fixed list, and `haus doctor` reports both read-only.

## Changing a setting without opening an editor

```sh
haus set theme.accent teal
haus get theme.accent       # teal
haus reset theme.accent     # inherit the desktop's value again
```

**Only `haus.*` paths are writable this way**, and the prefix is optional:
`theme.accent` and `haus.theme.accent` are the same path. A raw
`system.defaults.*` or `homebrew.*` path, or an option that doesn't exist, fails
before any file is written; those belong in your host file, via `haus edit`.
Values take the obvious shell form for strings and JSON for booleans, numbers,
lists and attribute sets.

`set` takes as many pairs as you like and applies them in **one** rebuild, so a
single intent spanning two options never leaves the machine half-switched:

```sh
haus set theme.flavor latte theme.systemAppearance flavor
```

Pairs are all-or-nothing: one rejected value rolls the whole call back, and `unset`
and `reset` take lists for the same reason. They differ in one place. `reset`
deletes the override, so whatever your host file or desktop says underneath
becomes effective again, and a path that had no override is reported rather than
fatal. `unset` writes `null` unconditionally, so it succeeds only where the
option's type admits `null`.

When you don't know what a setting is called, `haus set` with no arguments asks
instead, searching path *and* description, so `light mode` finds `theme.flavor`
as readily as `flavor` does. Tab completion knows the same list, `haus set
<TAB>` and likewise for `get`, `unset` and `reset`. Both read a static catalogue
installed with your build rather than evaluating your configuration, so they
describe the revision you have pinned and `haus update` moves them with it.

### One key inside an option

A path may go *inside* an option rather than merely up to it:

```sh
haus set bar.items.aiUsage true              # one pill, not the whole bar
haus set displays.internal.uiScale larger-text
```

**Prefer the leaf.** Overrides are written with `lib.mkForce`, so naming the
enclosing set (`haus set bar.items '{"aiUsage":true}'`) forces the *whole* set,
and every pill you didn't name falls back to its own default.

A misspelled sub-option is refused before anything is written. Keys you invent
yourself (a display's UUID, say) are taken as given, and what sits under them is
checked instead. A path and one of its ancestors can't both hold an override:
the second is refused, naming the first and the `haus reset` that clears it.

### Where the setting lives

`haus set` writes an ordinary Nix module to
`~/.config/nix/hosts/<hostname>/settings/<path>.nix` and stages it, because a
git-backed flake ignores untracked files. The file *is* the setting, and neither
`set` nor `reset` commits or pushes for you.

<Callout title="Also in the launcher">
The [launcher](/docs/haus/rooms/launcher)'s **Haus Settings** command is the
same mechanism behind three intent-sized buttons: *Make text bigger*, *Switch to
light mode*, *High contrast on*. The palette keeps no settings of its own; it
calls `haus set`.
</Callout>

## Reading a desktop or room before you trust it

Every other command drives *this* Mac. `haus show` reads someone else's work:
what you run when a stranger hands you a desktop, and what you run on your own
before you publish one.

```sh
haus show ./writer.nix                     # a file you already have
haus show github:ada/writer-desktop        # one you don't
haus show git+https://git.example.org/ada/desktop
haus show file+https://example.org/writer.nix
```

A source is fetched into the Nix store and read there. Nothing in **your
config** is written: not your `flake.nix`, not your lock, not a vendored copy.
Name one desktop with `--file` where a repo holds several.

**A desktop is data haus can check. A room is code, and haus can tell you
nothing about what it does.** What it can check it checks against the same rules
[`checkDesktop`](/docs/haus/desktops/creating#prove-the-boundary) enforces at
rebuild time, and it lists the rooms the desktop says nothing about beside the
ones it sets, because what a desktop leaves alone is half of what you are
agreeing to. A module function is called a room on sight, so a room is a
warning, not a verdict; *desktop* is only ever the checker's answer.

A fetched source also reports the revision it resolved to and two dates that are
easy to confuse: `changed`, its own commit date, and `fetched`, the clock as
this command ran, which no lock file records. A `file+https://` URL has neither,
since it pins content and nothing else, and a later `nix flake update` on one
prints the **same URL on both sides of its arrow** while the content moves
underneath. `show` says so where the shape is chosen.

<Callout type="info" title="Fetching and reading are two separate acts">
`show` never runs what it reads. The fetch pulls a *tree* without locking a
flake, so not even a room's own `flake.nix` is evaluated, and the read runs
restricted, where no fetch of any scheme resolves.

One honest limit: the restriction's unit is the store path, so a desktop fetched
from a repo can read the other files **its publisher shipped beside it**. It
still cannot read anything of yours.
</Callout>

### What would change here

On a machine that has a haus config, a passing desktop is compared against your
own, leaf by leaf: the ones it changes, the ones it turns off, and the ones your
own config outranks.

**A line in your host file outranks any desktop.** A desktop has to lose to the
person who chose it, but that means a stranger's file can be full of opinions
that do nothing on your Mac and no error anywhere says so. **A list your host names is replaced whole,
not merged**: lists combine only between definitions of equal rank, so the
desktop's entries never add to yours.

Three things it will not guess at. A leaf inside a list-like option
(`haus.roster.<app>.key` and its kind) has no option of its own to rank, so the
values are shown and the winner is not; `haus plan` settles that. A leaf your
haus has never heard of is a **version gap**, not a bad desktop, so `haus
update` is the answer and not the file. And a leaf this desktop turns off goes
back to *whatever haus decides*: that value is recorded nowhere on your machine,
so no number is printed for it.

This is a **leaf diff, not a rebuild preview**: turning a room off moves
packages, files and services that nothing here counts, and
[`haus plan`](#looking-before-you-leap) builds that answer. It evaluates *your*
flake and never the stranger's, and writes nothing, your lock included: if your
`flake.lock` would have to change to answer, `show` says so and skips the
section. `--no-diff` skips it outright, and a machine with no haus config never
sees it, which is what a publisher's CI wants.

For CI, the exit code is the contract:

| Exit | Means |
|---|---|
| `0` | It is a desktop and it passed, or it is a room and you passed `--room`. |
| `1` | It was checked as a desktop and it failed; every rule is listed. |
| `2` | It could not be fetched or read, or the arguments were wrong. |
| `3` | It is code and you did not say `--room`, so nothing was checked. |

`--json` prints the whole report on stdout instead, with `class`, `checked`,
`ok`, `failures`, `sets`, `silent`, `origin` (`null` for a local file), and
`machine` (`null` when there was nothing to compare against, otherwise one
verdict per leaf: `changes`, `unchanged`, `overridden`, `unranked`, `unknown`,
plus the leaves turned off). On a machine that has no haus, a publisher's CI
runner say, the same command is one `nix run` away:

```sh
nix run github:hausfold/haus#show -- ./writer.nix
nix run github:hausfold/haus#show -- github:ada/writer-desktop
```

## Pinning a desktop you found

`haus add` brings it in, rerunning the same check and refusing whatever `show`
would have. It writes `flake.nix` (the input, and the `desktop` line) and
`flake.lock` in one edit, after asking and defaulting to no. Nothing rebuilds;
`haus rebuild` is the next step.

```sh
haus add github:ada/writer-desktop
haus add --as writer --file writer.nix github:ada/desktops   # name it, pick the file
haus add --vendor file+https://example.org/writer.nix        # copy it in, don't pin it
haus add --print git+https://git.example.org/ada/desktop     # show the edit, write nothing
haus add -y github:ada/writer-desktop                        # skip the prompt
```

`--vendor` is the by-hand path (`curl`, `mv`, `git add`) done for you: the file
lands at `desktops/<name>.nix` in your config instead of becoming a flake input,
which is the right call for a one-off you plan to edit yourself. Pinning is the
default because it is how you get `haus update <name>` later. Only one
third-party desktop can be pinned at a time; a second `haus add` prints the
lines to add by hand rather than guessing at your `flake.nix`.

## Pinning a room

A room being code means an ordinary nix-darwin module that can install packages,
write files and run activation scripts as root. `haus add` takes one, but only
when you say so, and it never guesses which `haus.<ns>` the room means to own:

```sh
haus add --room --namespace photography github:ada/photo-room
```

`--namespace` is required, and repeatable for a room that claims more than one.
It can't be inferred, because learning it means running the room's code. Add
`--module <attr>` when the room's flake exports it as something other than
`darwinModules.default`. `--file` and `--vendor` don't apply: a room is a flake
input, not a file you can copy in.

<Callout type="warn" title="A room's confirmation is typed, and -y can't skip it">
Pinning locks the input, and locking a flake evaluates its `flake.nix`, so the
room's code has already run by the time anything lands in yours. That is why the
prompt names the revision and asks you to type its first twelve characters back,
and why neither `-y` nor `--yes` answers it. With no terminal attached the
answer is a per-name environment variable set to the **full** revision, so a
piped installer can never accept a room on your behalf with one blanket switch.
The name is `HAUS_ADD_ROOM_` plus the input's own name, uppercased, with every
character that isn't a letter or a digit turned into `_`: the `photo-room` above
wants `HAUS_ADD_ROOM_PHOTO_ROOM`.
</Callout>

One room at a time, the same scope the desktop side keeps. `haus add --print`
shows the whole edit first (the input, the `extraModules` line, one
`haus._rooms.claimed.<ns>` per namespace) and writes nothing. `haus remove
<name>` takes the `extraModules` entry out along with the input, then stops
short: it can't tell which namespace claim belonged to that room, so it prints
the `haus reset _rooms.claimed.<ns>` for you to run.

## Looking before you leap

`haus rollback` rewinds everything Nix owns, atomically. It does **not** rewind
macOS's own preferences: activation writes those imperatively, into
`com.apple.dock`, Finder, `NSGlobalDomain` and friends, and no generation holds
them. Four commands close that gap:

```sh
haus plan        # what the next rebuild would change, before it changes it
haus diff        # what the running config set vs what macOS has right now
haus capture     # snapshot the settings a rebuild is about to move
haus revert-settings   # put that snapshot back
```

`capture` before a risky change and `revert-settings` after is the
macOS-defaults equivalent of a generation rollback. It defaults to the Dock,
keyboard and Finder; name a plist domain to reach anything else. Neither trusts
a hand-kept list: both read the built activation script and probe macOS live for
the accessibility keys it accepts silently and then ignores.

`plan` reports packages, macOS settings, **the files written into your home**
(with the `onChange` hooks each would fire), launchd jobs and new casks. Files
an activation script writes rather than links stay outside that set and won't
appear.

<Callout type="warn" title="`plan` reads your config directory, not the one you're standing in">
`haus` always evaluates `~/.config/nix` unless you tell it otherwise. Run `haus
plan` from a linked git worktree of that config (an agent lane, say) and it
previews the config on `main`, not the branch you're looking at. It warns and
names both paths; point it at the tree you mean:

```sh
HAUS_CONSUMER="$(git rev-parse --show-toplevel)" haus plan
```
</Callout>

## When a rebuild fails

A rebuild that fails leaves you holding a Nix trace and a machine that did not
change. [The AI room](/docs/haus/rooms/ai) offers to read that trace for you;
its **Fix it** button runs `haus fix`, and so can you.

```sh
haus fix              # fix the rebuild that just failed
haus fix --dry-run    # print what the agent would be told, and run nothing
```

It gives the client `haus.ai.default` names one turn in `~/.config/nix`, with
the failing phase, the error, what changed in your config since the last good
rebuild, and the haus revision you are pinned to. Then it checks the answer
itself, since the config has to evaluate again. The transcript is
`~/.local/state/haus/fix.log`, and `HAUS_NO_FIX=1` turns the offer off for a
rebuild without turning the room off.

Two things it will not do:

- **It never activates.** Applying the fix is `haus rebuild`, and that stays
  yours to run.
- **It never runs where there is no undo.** The agent works with its permission
  prompts off, because the offer is meant to be answerable from a notification
  when nobody is watching the terminal. What bounds it instead is that it works
  in `~/.config/nix` and nowhere else, and leaves its whole change as one
  commit:

  ```sh
  git -C ~/.config/nix revert HEAD    # undo everything it did
  ```

  So if `~/.config/nix` is not a git repository the offer is never made, and
  `haus fix` refuses: there would be nothing to revert. The one break with no
  commit behind it is the edit you had not saved yet. Fixing that means undoing
  it, so `HEAD` never moved and reverting would undo the last thing that was
  fine. `haus fix` says so instead of printing the line above.

## The one rebuild it refuses

A host file that writes `system.defaults.universalaccess.*` directly needs
**Full Disk Access** for the app the rebuild runs under, and `haus rebuild`
refuses up front without it. That domain is TCC-protected and the grant follows
the app rather than the person, so a plain terminal nobody has granted is refused
and an agent pane inside a granted one goes through. That is the kinder failure:
the write would otherwise abort activation partway and take everything after it
down, leaving your bar, tiling and palette dead with the symptom nowhere near the
cause. Refused, nothing has changed and your edit is still on disk.

`haus plan` says which grant a rebuild wants before it runs, `haus doctor`'s
**Permissions** section whether this app has it. `haus.accessibility.*` sidesteps
the domain with a guarded write, so a missing grant costs that setting and
nothing else, and `HAUS_FDA_ANYWAY=1` overrides (`HAUS_AGENT_REBUILD=1` is an
accepted alias). `haus.theme.contrast` is unrelated: haus's own palette axis,
painted into the apps haus themes, so it always applies.

## Colour, and what a pipe gets

Colour is written only when `haus`'s output *is* a terminal and `NO_COLOR` is
unset; `CLICOLOR_FORCE=1` forces it back on through a pipe, for `less -R`.

```sh
haus status                    # painted
haus status | tee status.txt   # plain text, no escapes in the file
NO_COLOR=1 haus status         # plain text, on the terminal too
CLICOLOR_FORCE=1 haus status | less -R
```

A rebuild's phase lines follow the same fence: a live region repainted in place
on a terminal, one plain line per phase into a pipe, a file, CI or an agent
pane. `haus show` and `haus-activate` obey the rule too, so a publisher's CI log
and a failed activation's message are both plain text by default.
