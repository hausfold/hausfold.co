A **rice** is a single `.nix` file whose only top-level key is `haus`. That is
the entire format, and the smallness is the point: a rice can't run a script,
reach a macOS setting haus doesn't already expose, or hand the build a package
of its own. A stranger can read one in a minute and know the worst it can do —
which is what makes importing one from someone you've never met reasonable.

haus ships four of its own, as
[presets](/docs/haus/guides/making-it-yours#starting-from-someone-elses-rice).
This page is how you write yours.

## The format

```nix
{
  haus = {
    developer.enable = false;
    prowl.enable = false;
    keys.leader = "none";

    theme = {
      flavor = "latte";
      accent = "rosewater";
    };

    sill.items.weather = false;
  };
}
```

There is no `{ pkgs, lib, config, ... }:` header — this is data, not a module
function. No `system.defaults`, no `pkgs`, no activation hooks. Everything stays
inside the documented
[`haus.*` option surface](https://nebelhaus.com/reference/options/).

<Callout title="A whole rice, or a layer?">
A **whole rice** describes a kind of machine or a kind of person, and picks all
the big rooms — developer tools, tiling, the bar, the launcher. A **layer**
describes one concern, like larger type, and sets only what that concern needs.
Layers stack on anything; whole rices collide with each other.
</Callout>

## Teach it your own first lap

The built-in tour teaches haus's core moves in the bar, one hint at a time. A
rice can replace that lap with its own and stay data-only — and a rice that turns
rooms off usually must, because the built-in one is leader moves plus the
launcher and has nothing left to teach without them:

```nix
haus.tour.steps = [
  {
    hint = "Press {palette}, type tour, then hit ↵";
    detect = "palette";
  }
  {
    hint = "Move to another workspace";
    detect = "workspace";
  }
];
```

Steps run in order and advance on signals haus already emits, never on
keystrokes. `detect` takes one of `launch`, `workspace`, `navigate`, `resize` or
`palette`; the first four need prowl, and `palette` needs the launcher *and* a
palette key bound. A left click skips a step. Left at its default `null`,
`tour.steps` keeps the built-in lap — an **empty** list is a type error, and the
off switch is `tour.enable = false`.

**Write keys as `{palette}`, `{leader}` and `{leaderName}`, never as a literal
chord.** They expand to what *that* machine resolved, so a tour you share still
names the right keys on a rice that moved `keys.palette` — where a hardcoded
`⌘Space` would be wrong invisibly, since you never see the consumer's bar. A
misspelled placeholder renders as typed, and the rebuild warns and names it.

<Callout type="warn" title="The tour is drawn by the bar">
A rebuild warns when a step needs a room the rice switched off — but those
warnings live inside sill's own module, so a rice that turns the bar off gets
none of them. Check that pairing by eye.
</Callout>

## Prove the boundary

Run the same structural check haus runs against its own presets:

```sh
nix eval --impure --expr \
  '(builtins.getFlake "github:hausfold/haus").lib.checkRice ./writer.nix'
```

It prints `true`, or throws naming what escaped — a stray top-level key, or the
file being a function rather than data. If the file is an app **pack** — a rice
narrowed to `haus.roster`, the apps on a machine — run `lib.checkPack` instead;
same rule, one level in.

`checkRice` proves the trust boundary and nothing more: it does not prove an
option name or a value is valid. For that, import the rice into a real host and
evaluate it:

```nix
extraModules = [ ./rices/writer.nix ];
```

```sh
nix eval .#darwinConfigurations.myhost.system.drvPath
```

[`haus plan`](/docs/haus/reference/haus) is the stronger version of that last
step: it prints what a rebuild *would* change — packages, settings, files,
launchd jobs, casks — and changes nothing. It builds first, so it takes longer
than the eval above; it tells you correspondingly more.

## Prove it composes

Test it combined, not just alone:

```nix
extraModules = [
  ./rices/writer.nix
  nebelhaus.presets.large-print
];
```

Try four things: the rice alone; the rice plus an unrelated layer; a host value
set on top of one of the rice's own choices; and each combination of rooms it
turns off. The middle two need neither a Mac nor a build — composing two rices
over the option surface takes seconds.

**Two rices compose unless they *disagree*.** Import order carries no priority in
Nix, so "imported last, therefore wins" is not a mechanism you can lean on in
either direction — but naming the same option is not the problem people assume.
Same option and the same value merges silently and costs nobody anything. Same
option, *different* values stops the build:

```text
error: The option `haus.sill.enable' has conflicting definition values:
       - In `…/presets/minimal.nix': false
       - In `…/presets/everyday.nix': true
       Use `lib.mkForce value` or `lib.mkDefault value` to change the priority…
```

The option, both files, and the fix. Your consumer resolves it with `lib.mkForce`
in their host file — so that line belongs in your README for every field you set
that a reasonable person might disagree with. Narrow the rice until ordinary
merging is enough: every optional field you set is one somebody has to force.

<Callout type="warn" title="The quiet half — a list never conflicts, it combines">
That error only happens for options holding a single value. A **list**-typed one
— `tour.steps`, `keys.leaderExtras`, `snippets.matches` — never conflicts at all:
the definitions are combined, with no error and no warning. Two rices that each
author one tour step produce a tour with both, in an order neither author chose.
Worse, it can surface later as something else: two rices each adding a leader key
merge quietly, and *then* prowl asserts that leader keys are unique.

**Attribute sets are the middle case.** `roster`, `workspaces` and
`pounce.items` merge per key, so two rices naming different apps compose, while
two naming the same app's same field conflict as loudly as any single value.

If your rice sets any of these, say so in its README, and say whether it expects
to be the only one.
</Callout>

<Callout title="App packs are the exception">
A pack is imported through `nebelhaus.lib.pack`, which lowers every field it
sets so the consumer's own host wins with a plain assignment and no `mkForce`.
That is a property of the seam, not of the file — the same pack imported as a
bare path still conflicts. Presets are deliberately not wrapped that way.
</Callout>

## Publish something inspectable

The smallest useful repository is deliberately boring:

```text
writer-rice/
├── README.md
├── writer.nix
└── LICENSE
```

In the README, say who the rice is for and what it changes; whether it is a whole
rice or a layer; which haus revision you tested against; how to import it; what
it deliberately doesn't handle, including rooms or permissions it expects; and
whether both `checkRice` and a real host evaluation passed.

For a first release, invite people to review and vendor the `.nix` file. A remote
flake wrapper can come later if versioned imports turn out to be useful — it
should not hide the data people are being asked to trust, and any wrapper owes
every module it rebuilds a `_file`, or the conflicts it causes name no file at
all.

## What doesn't belong in one

Keep these in a private host file, or in something honestly labelled as more
powerful:

- identity, secrets, tokens and personal account names;
- an app roster that reveals more than the rice needs;
- raw macOS defaults outside `haus.*`;
- a `pkgs` value, or a `/nix/store` path;
- activation hooks and shell commands;
- a display UUID — `haus.displays.main` says "the screen this Mac is using"
  without naming anyone's hardware.

Naming a *package* is fine and doesn't need `pkgs`: options that take one have a
`packageName` sibling taking the nixpkgs attribute as a string, so a rice can
change the mono font or add a tool without leaving the data-only surface. A
configuration that genuinely needs `pkgs`, scripts, or arbitrary nix-darwin
options is a **power module**, and carries a different trust model.

## Before you share

- [ ] `checkRice` prints `true`, and a real host evaluates.
- [ ] The rice composes with an unrelated layer.
- [ ] Every field it sets is in the README with the `lib.mkForce` line a consumer
      needs — or, for a pack, it's imported through `nebelhaus.lib.pack` so they
      don't need one.
- [ ] If it sets a list, the README says so, because a second rice setting the
      same one merges into it silently.
- [ ] Rooms it turns off agree with the features that depend on them,
      `tour.steps` included.
- [ ] The README states the audience, the scope, the tested revision and the
      limits.
- [ ] There is no identity, secret or device-specific data anywhere in it.
